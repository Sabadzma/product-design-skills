# Update UX documentation

Start on explicit invocation or when another UX documentation skill routes the user’s request here. On a handoff, follow the linked skill through completion with the same project, context, and scope. Report whether the docs already existed and what changed, including when no edits were needed.

1. Locate the existing `ux-docs/` folder at the target project root or the path the user specified. If the path points to the `ux-docs` skill package, resolve the target project before editing. If the folder is missing, use [scaffold-ux-docs](../scaffold-ux-docs/SKILL.md) for a starter-files-only request. For a request to document decisions, scenarios, or project materials, use [ux-docs](../ux-docs/SKILL.md) to create the first docs from that context.
2. For a conversation handoff, gather confirmed UX decisions that still apply from the relevant discussion and any additional decisions the user explicitly includes. Look back through that discussion for earlier agreements. For other maintenance, use the scope the user specified.

   During an update requested by the user, record only concrete design-review situations the user personally raised or explicitly selected. Preserve their meaning and wording. A documented flow, rule, or agent suggestion alone does not qualify. On a handoff from `ux-docs`, skip scenario capture. For eligible entries, reuse matching bullets in the owning feature’s `scenarios.md`, use the [scenario format](../ux-docs/references/folder-structure.md#feature-scenarios), and link the file from its feature README. If an update requested by the user needs first-time docs, finish the creation handoff and then capture the eligible entries here. Only an explicit request for `explore-ux-scenarios` starts scenario discovery.

3. Read the in-scope materials and compare them with each other and the existing rules. If they give incompatible answers about the same behavior under the same conditions, check whether a confirmed change already settles the difference. Follow the [conflict workflow](../ux-docs/references/conflicting-decisions.md) before editing when a conflict is unresolved.

   When a conflict is unresolved and the reference is unavailable, ask whether to resolve conflicts one at a time or list them under `## Open questions`, and wait for the choice. In Q&A, present the options and sources for one conflict and wait for an answer before moving on. For each unresolved or deferred conflict, add or update one question in the owning feature's `decisions.md` with the options and sources. Keep the existing rule in effect until a replacement is confirmed and remove the matching open question when resolved.

4. Check the [product overview](../ux-docs/references/folder-structure.md#product-overview) using the information available for this task. Populate a missing, empty, or placeholder-only `product-overview.md` when the sources or existing UX docs support a basic description. Enrich it when you learn a meaningful product-level fact about its purpose, core logic, or key capabilities, even if the existing description still holds. Edit only the relevant part. Keep screen descriptions, detailed feature behavior, and decisions in the feature docs.
5. For a decision handoff, write any supported overview updates even when there are no new decisions or open questions. Record each decision in the `decisions.md` that owns its rule and follow the [decision format](../ux-docs/references/folder-structure.md#decision-format) for every entry you create or revise. Organize the result around the feature's rules and flows, regardless of the source's structure, length, or style. Keep unaffected entries and stable headings in place.
6. In `decisions.md`, use one level-two heading per rule or flow and one behavior paragraph of one to three sentences, up to 60 words. State the applicable trigger, condition, and outcome in plain present-tense language. Include exceptions only when they change what happens. Use a separate rationale sentence of up to 25 words for a consequential choice when the source explains it. Link to shared rules at their source. Use the [shared templates and file roles](../ux-docs/references/folder-structure.md) for new files when available.
7. Search for references to affected headings and terms to find dependent flows. Update their links, local outcomes, summaries, and glossary entries only where the scoped change affects them. Repair incoming links when a target moves. Keep any superseded rationale separate from the current entry.
8. Before finishing, compare the document types you touched with the [worked example](../ux-docs/references/folder-structure.md#worked-example) when available. Check the decision format and limits, keep only source details that affect the rule, and verify affected links. Report what changed, any overview details you could not establish, and what still needs a decision.
